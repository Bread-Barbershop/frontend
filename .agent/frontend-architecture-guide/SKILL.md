# 프론트엔드 아키텍처 온보딩

## 이 스킬을 언제 사용할까

다음과 같은 상황에서 이 스킬을 사용한다:

- 프로젝트 구조를 먼저 이해해야 할 때
- 어떤 기능을 어디 레이어에 구현해야 할지 판단해야 할 때
- 상태 흐름, 데이터 흐름, API 흐름을 추적해야 할 때
- 수정 전에 이 프로젝트의 아키텍처 경계를 이해해야 할 때
- 일반적인 DB 중심 웹 서비스처럼 해석하면 안 되는 프로젝트일 때

## 이 스킬의 목표

이 스킬은 AI가 아래 내용을 빠르게 이해하도록 돕는다:

- 이 프로젝트가 일반적인 웹 서비스와 어떻게 다른지
- 어떤 폴더가 어떤 책임을 가지는지
- 기능 수정 시 어디부터 추적해야 하는지
- 어떤 실수를 특히 조심해야 하는지

## 프로젝트 핵심 요약

이 프로젝트는 일반적인 중앙 서버 + 중앙 DB 구조가 아니다.

핵심 특징:

- 서비스 운영자가 사용자 데이터를 직접 보관하지 않는다.
- 사용자 데이터는 Google Drive에 JSON 형태로 저장된다.
- 별도 백엔드 서버가 없어 보이더라도, Next.js의 `app/api/**`, 서버 컴포넌트 기반 fetch, 캐시 재검증(`revalidate*`) 흐름이 사실상 서버 역할을 수행한다.
- “DB가 없다”는 뜻은 저장이 없다는 뜻이 아니라, 중앙 DB 대신 Google Drive를 저장소로 사용한다는 뜻이다.
- “서버가 없다”는 뜻은 백엔드 로직이 없다는 뜻이 아니라, Next.js 서버 기능이 이를 대체한다는 뜻이다.
- 멀티 유저 시스템이지만 중앙 세션 서버 대신 OAuth 기반 인증 흐름을 사용한다.

## 이 프로젝트를 이해하는 기본 관점

이 프로젝트는 아래 레이어 관점으로 읽는다:

- `app/`: 페이지 진입점, 라우팅, URL 기반 흐름
- `app/api/`: 인증, Google Drive 연동, 저장/조회/배포 같은 서버 엔드포인트와 서버 유틸
- `widgets/`: 특정 화면 맥락에서 여러 요소를 묶는 조합 레이어
- `components/organisms/`: 초대장 블록 단위의 실제 기능 구현 레이어
- `shared/`: 공통 타입, 유틸, 레지스트리, 전역 상태, 정적 리소스

도메인은 “초대장 블록 + 메인 포스터 + BGM” 축으로 이해한다.
블록 타입, 필드 구조, 컴포넌트 매핑 같은 핵심 개념은 `shared/data/registry/**`, `shared/types/**`를 중심으로 보고, 각 블록의 상세 구현은 `components/organisms/**`에서 확인한다. 다만 `mainPoster`는 일반 블록 레지스트리 바깥의 별도 축이므로 `widgets/mainPoster/**`와 관련 상태 컨텍스트를 함께 봐야 한다.

상태는 한 곳에만 모여 있지 않다.
편집기 전역 상태, 메인 포스터 상태, BGM 상태 등은 목적별로 분리되어 있으므로 단일 source of truth로 오해하면 안 된다.

## 폴더/레이어 역할

### `app/`

- 역할: 사용자 화면의 진입점, 라우팅, 페이지 흐름 제어
- 넣어야 하는 것: `page.tsx`, `layout.tsx`, 라우트 단위 초기 데이터 연결, 페이지 수준 조립
- 넣으면 안 되는 것: 재사용 가능한 블록 UI 구현, 전역 공통 유틸, 세부 편집 기능 로직
- 같이 봐야 하는 폴더: `widgets/`, `components/organisms/`, `shared/`, `app/api/`

### `app/api/`

- 역할: 인증, Google Drive 연동, 저장/조회/배포 같은 서버 엔드포인트와 서버 유틸
- 넣어야 하는 것: `route.ts`, 서버 인증 처리, 외부 API 호출, 쿠키/세션 처리, Drive 연동 로직
- 넣으면 안 되는 것: 브라우저 전용 UI 코드, 클라이언트 컴포넌트, 화면 조립 로직
- 같이 봐야 하는 폴더: `app/`, `shared/`

### `widgets/`

- 역할: 특정 화면 맥락에서 여러 컴포넌트와 상태를 묶는 화면 단위 조합 레이어
- 넣어야 하는 것: 편집 화면 패널, 미리보기, 화면 전용 컨텍스트/훅/유틸
- 넣으면 안 되는 것: 범용 공용 컴포넌트, 블록 표준 정의, 서버 엔드포인트
- 같이 봐야 하는 폴더: `app/`, `components/organisms/`, `shared/store/`

### `components/organisms/`

- 역할: 초대장 블록 단위의 실제 기능 구현과 편집/미리보기 표현
- 넣어야 하는 것: 블록별 컴포넌트, 각 블록의 `schema`, `definition`, preview/edit 구현
- 넣으면 안 되는 것: 페이지 라우팅 책임, 에디터 전체 화면 조립 책임, 전역 상태 저장소
- 같이 봐야 하는 폴더: `shared/data/registry/`, `shared/types/`, `widgets/editor/`

### `shared/`

- 역할: 여러 레이어에서 공통으로 쓰는 타입, 유틸, 전역 상태, 레지스트리, 정적 리소스 제공
- 넣어야 하는 것: 공통 타입, 범용 유틸, store, 블록 레지스트리, 템플릿 데이터, 공용 리소스
- 넣으면 안 되는 것: 특정 페이지 전용 로직, 특정 화면 조합에 강하게 종속된 구현, 개별 블록의 상세 UI
- 같이 봐야 하는 폴더: `app/`, `app/api/`, `widgets/`, `components/organisms/`

## 작업을 분석하는 순서

### 버그 수정일 때

1. 문제가 발생하는 화면의 진입점이 `app/**` 어디인지 먼저 확인한다.
2. 그 페이지가 어떤 `widgets/**`와 `components/organisms/**`를 조합하는지 추적한다.
3. 상태 시작점과 store/context 위치를 확인한다.
4. 블록 구조나 도메인 규칙이 관련되면 `shared/data/registry/**`, `shared/types/**`를 본다.
5. 저장/조회/인증/배포가 관련되면 `app/api/**`와 관련 클라이언트 호출 지점을 함께 확인한다.
6. 수정 대상이 `shared/**`나 공용 컴포넌트에 있으면 다른 화면 영향도 함께 점검한다.

### 새 기능 추가일 때

1. 이 기능이 페이지 책임인지, 화면 조합 책임인지, 블록 책임인지, 공통 책임인지 먼저 판단한다.
2. 페이지 흐름이면 `app/`, 화면 조합이면 `widgets/`, 블록 기능이면 `components/organisms/`, 공통 기반이면 `shared/`, 서버 연동이면 `app/api/`를 우선 고려한다.
3. 상태는 기존 store/context 체계 안에 넣을지, 로컬 상태로 둘지 먼저 판단한다.
4. 새로 만들기 전에 유사한 구현이 이미 있는지 먼저 찾는다.
5. Google Drive 저장 구조나 인증 흐름과 연결되면 프론트 변경만 보지 말고 `app/api/**`까지 함께 본다.

### 리팩터링일 때

1. 현재 로직의 실제 소유 레이어를 먼저 확인한다.
2. `app -> widgets/components -> shared` 흐름을 기준으로 의존 방향이 뒤집히지 않았는지 본다.
3. 여러 곳에서 재사용되고 특정 화면/블록 맥락에 묶여 있지 않을 때만 `shared/**`로 올린다.
4. 레이어 경계(`app`, `app/api`, `widgets`, `components/organisms`, `shared`)를 흐리지 않는 방향으로 정리한다.

## 자주 하는 실수 / 주의할 점

- `app/`에 재사용 가능한 블록 UI나 공통 유틸을 넣지 않는다.
- `widgets/`를 범용 공통 컴포넌트 레이어로 오해하지 않는다. 이곳은 화면 맥락이 강한 조합 레이어다.
- 블록별 규칙과 필드 구조를 `app/`이나 저수준 UI 레이어에 넣지 않는다.
- 편집기의 상태를 하나의 source of truth로 단순화해서 해석하지 않는다.
- Google Drive 기반 구조를 단순 파일 업로드 기능 정도로 오해하지 않는다. 이 프로젝트에서는 Drive가 실질적인 데이터 저장소 역할을 한다.
- 저장/조회 문제를 볼 때는 클라이언트 코드만 보지 말고 `app/api/**`까지 함께 확인한다.

## 빠른 판단 기준

- UI 표현 수정이면: 먼저 해당 `app/**` 진입점 다음 `widgets/**`, `components/organisms/**`를 본다.
- 데이터 흐름 수정이면: `shared/store/**`, 관련 훅/컨텍스트, `app/api/**`를 함께 본다.
- 블록 구조 수정이면: `shared/data/registry/**`, `shared/types/**`, `components/organisms/**`를 함께 본다.
- 여러 화면에 영향이 있을 수 있으면: `shared/**`와 공용 컴포넌트 사용처를 함께 확인한다.
- 어디에 코드를 둬야 할지 애매하면: “이 로직이 특정 화면/특정 블록 맥락에 묶여 있는가?”를 먼저 판단한 뒤 레이어를 정한다.

## 먼저 확인해야 하는 파일/폴더

- `shared/data/registry/` — 블록 타입, 필드 구조, 매핑 등 도메인 구조를 빠르게 파악할 수 있다.
- `shared/store/editorStore/` — 편집기 전역 상태와 액션 흐름을 확인하기 좋다.
- `app/editor/[id]/` — 저장된 데이터를 불러와 편집기를 초기화하는 흐름의 중심이다.
- `widgets/mainPoster/` — 메인 포스터 편집기와 캔버스 관련 핵심 동작이 모여 있다.
- `components/organisms/` — 초대장 블록 단위의 실제 편집/미리보기 구현을 확인할 수 있다.
- `app/api/drive/` — Google Drive 기반 저장/조회/배포 흐름을 이해하는 핵심 위치다.
