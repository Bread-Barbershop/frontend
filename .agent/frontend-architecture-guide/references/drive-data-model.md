## 1. 핵심 개념

이 프로젝트는 앱 내부 데이터베이스 대신 사용자의 Google Drive를 저장소처럼 사용한다.
따라서 “저장한다”는 말은 서버 DB에 row를 넣는 것이 아니라, Drive 안의 폴더/파일 구조를 만들고 유지하는 것을 의미한다.

핵심 관점은 다음과 같다.

1. 워크스페이스 폴더가 최상위 저장 단위다.
2. 각 초대장은 워크스페이스 아래의 개별 초대장 폴더로 관리된다.
3. 초대장 폴더 안에는 `data.json`과 에셋 폴더(이미지/오디오)가 존재한다.
4. 공개 배포는 내부 DB publish 상태를 바꾸는 방식이 아니라, Drive 권한과 공개 URL 기반으로 이루어진다.

## 2. Drive 안에서의 데이터 구조

현재 코드 기준으로 Drive 구조를 단순화하면 다음과 같이 이해하면 된다.

```text
Google Drive
└── 나의 모바일 청첩장 (workspace folder)
    ├── 초대장 (invitation folder, inv_id/app metadata 보유)
    │   ├── data.json
    │   ├── images/
    │   └── audio/
    ├── 초대장 (...)
    └── 초대장 (...)
```

### 2.1 워크스페이스 폴더

- 서비스 전용 최상위 폴더다.
- 없으면 생성하고, 있으면 재사용한다.
- 앱 식별을 위해 `app_id` 기반 appProperties를 사용한다.

### 2.2 초대장 폴더

- 각 초대장 하나를 나타내는 폴더다.
- `inv_id`와 `kind=invitation` 같은 appProperties를 통해 식별한다.
- 사용자가 새 초대장을 만들면 새 폴더가 생성되고, 기존 초대장을 편집하면 같은 uuid의 폴더를 재사용한다.

### 2.3 `data.json`

- 초대장 본문 데이터의 핵심 파일이다.
- block 구조, mainPoster, bgm 관련 설정이 이 파일에 저장된다.
- 없으면 기본 payload로 생성된다.

### 2.4 에셋 폴더

- 이미지와 오디오 파일은 `data.json`과 별도로 관리된다.
- 일반적으로 초대장 폴더 아래 `images/`, `audio/` 역할의 하위 폴더가 보장된다.
- 실제 렌더링/편집 시에는 파일 목록과 fileId를 함께 사용한다.

## 3. 저장 흐름

저장 흐름의 핵심은 “필요한 Drive 구조를 먼저 보장한 뒤, 그 구조에 데이터를 기록한다”는 점이다.

일반적인 순서는 다음과 같다.

1. 클라이언트가 저장 시작 시점에 서버에 저장 준비를 요청한다.
2. 서버는 access token을 갱신/확보한다.
3. 워크스페이스 폴더가 있는지 확인하고 없으면 생성한다.
4. 초대장 폴더를 `invitationUuid` 기준으로 찾고, 없으면 생성한다.
5. `data.json` 파일이 있는지 확인하고, 없으면 기본 payload로 생성한다.
6. 이미지/오디오 에셋 폴더를 보장한다.
7. 필요한 fileId와 folderId를 클라이언트에 반환한다.

즉, 저장은 단순 POST 한 번으로 끝나는 개념이 아니라, **Drive 저장 구조를 준비하는 단계 + 실제 데이터 반영 단계**로 나누어 이해하는 것이 안전하다.

## 4. 수정/조회 흐름

기존 초대장을 다시 편집할 때는 초대장 폴더 안의 구조를 읽어서 편집기 상태로 복원해야 한다.

일반적인 조회 흐름은 다음과 같다.

1. 초대장 folder id를 기준으로 Drive 내부 파일 목록을 읽는다.
2. 하위 폴더 중 image/audio 폴더를 식별한다.
3. 각 폴더의 파일 목록을 수집한다.
4. `data.json` 파일 내용을 읽어 편집기 config로 복원한다.
5. 클라이언트는 이를 바탕으로 block, mainPoster, bgm 상태를 초기화한다.

즉, 조회는 단순 JSON 하나만 읽는 것이 아니라, **설정 데이터 + 에셋 메타데이터를 함께 구성하는 과정**이다.

## 5. 공개 배포 흐름

공개 배포는 일반적인 “DB의 published 컬럼 변경”과 다르다.
이 프로젝트에서는 Drive 권한과 공개 URL이 핵심이다.

일반적인 배포 흐름은 다음과 같다.

1. 서버가 초대장 폴더 안의 `data.json` 파일을 보장한다.
2. 초대장 폴더의 공개 권한을 설정하거나 재확인한다.
3. 공개 가능한 guest URL을 계산한다.
4. guest 페이지 캐시를 무효화한다.
5. 공개된 `data.json` URL이 실제로 읽히는지 짧게 probe/retry 한다.
6. 읽기 가능하고 payload schema가 유효한 것이 확인되면 guest URL을 성공 응답으로 반환한다.

즉, 배포는 단순 권한 변경이 아니라 **권한 설정 + 캐시 무효화 + 공개 데이터 검증**까지 포함하는 흐름이다.

## 6. `data.json`의 의미

`data.json`은 이 프로젝트에서 가장 중요한 데이터 파일이다.
현재 코드 기준 기본 구조는 대략 다음 필드를 가진다.

- `blocks`: 초대장 블록 목록
- `bgm`: 배경음악 설정
- `mainPoster`: 메인 포스터 데이터

중요한 점:

- 이 파일이 초대장 본문 상태의 중심이다.
- 공개 게스트 페이지도 결국 이 JSON을 읽는다.
- 새 초대장을 만들 때 기본 payload가 자동으로 초기화된다.
- JSON 스키마가 깨지면 공개 렌더링과 편집기 복원이 모두 영향을 받을 수 있다.

따라서 `data.json` 구조를 변경하는 작업은 단순 프론트 수정이 아니라 **저장/복원/공개 렌더링 전체에 영향을 주는 변경**으로 봐야 한다.

## 7. 자주 하는 오해

### “DB가 없으니 persistence가 없다.”

틀린 해석이다.
Persistence는 존재하며, 다만 Drive 기반 파일/폴더 구조로 관리될 뿐이다.

### “저장은 `data.json`만 저장하면 끝난다.”

불완전한 해석이다.
실제로는 초대장 폴더, `data.json`, 이미지 폴더, 오디오 폴더 등 저장 구조 전체를 함께 봐야 한다.

### “공개 배포는 URL만 만들어서 끝난다.”

틀린 해석이다.
권한 설정, 캐시 무효화, 공개 JSON 검증까지 포함된다.

### “편집기 조회는 JSON 하나만 불러오는 작업이다.”

불완전한 해석이다.
편집기 복원에는 JSON config뿐 아니라 이미지/오디오 파일 목록도 함께 필요하다.

### “공개 게스트 페이지도 내부 API 응답을 바로 받아 렌더링한다.”

틀린 해석이다.
공개 게스트 페이지는 공개된 Drive JSON을 fetch해서 렌더링한다.

## 8. 문제를 추적할 때 보는 위치

### 저장 구조가 안 만들어질 때

- `app/api/drive/saveInvitation/route.ts`
- `app/api/drive/_lib/ensureWorkspace.ts`
- `app/api/drive/_lib/ensureInvitationFolder.ts`
- `app/api/drive/_lib/ensureDataJsonFile.ts`

### 기존 초대장을 복원할 때 데이터가 이상할 때

- `app/api/drive/updateInvitation/route.ts`
- `app/editor/[id]/types/savedata.ts`

### 공개 배포 후 게스트 페이지가 안 열릴 때

- `app/api/drive/publishInvitation/route.ts`
- `app/guest/[id]/page.tsx`

### 초대장 목록이 이상할 때

- `app/api/drive/loadInvitation/route.ts`

문제를 볼 때는 항상 “이 이슈가 저장 준비 단계인지, 기존 데이터 복원 단계인지, 공개 배포 단계인지”를 먼저 구분한 뒤 파일을 여는 것이 좋다.
