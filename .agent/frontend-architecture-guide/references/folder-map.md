# 폴더 맵

## 문서 목적

이 문서는 이 프로젝트에서 **어디에 무엇을 둬야 하는지** 빠르게 판단하기 위한 폴더 책임 가이드다.
새 기능을 추가하거나 기존 기능을 수정할 때, 먼저 이 문서를 보고 변경 대상이 어느 레이어에 속하는지 판단한다.

## 1. 판단 원칙

코드를 둘 위치가 애매하면 아래 순서로 판단한다.

1. **이 코드가 라우트 진입과 URL 흐름을 다루는가?** → `app/`
2. **이 코드가 서버 연동, 인증, 저장/조회/배포를 다루는가?** → `app/api/`
3. **이 코드가 특정 화면 맥락에서 여러 요소를 조합하는가?** → `widgets/`
4. **이 코드가 초대장 블록 자체의 동작을 구현하는가?** → `components/organisms/`
5. **이 코드가 여러 레이어에서 재사용되는 공통 기반인가?** → `shared/`
6. **이 코드가 저수준 UI primitive인가?** → `components/atoms/` 또는 `components/molecules/`

핵심 원칙은 **“재사용 가능해 보인다”만으로 `shared/`에 넣지 않는 것**이다.
특정 화면, 특정 블록, 특정 흐름에 강하게 묶여 있으면 해당 맥락 레이어에 남겨야 한다.

## 2. 최상위 폴더 역할

### `app/`

- 역할: 페이지 진입점, 라우팅, URL 기반 흐름, 페이지 수준 조립
- 대표 예시: 홈, 편집기 진입, 공개 초대장 페이지
- 넣어야 하는 것: `page.tsx`, `layout.tsx`, 라우트 파라미터 처리, 페이지 초기화
- 넣으면 안 되는 것: 재사용 블록 구현, 범용 유틸, 서버 전용 로직

### `app/api/`

- 역할: 인증, Drive 연동, 저장/조회/배포 등 서버 통합 레이어
- 대표 예시: `auth`, `drive`, `place`
- 넣어야 하는 것: `route.ts`, 서버 전용 유틸, 외부 API 호출, 토큰/세션 처리
- 넣으면 안 되는 것: 브라우저 UI, 클라이언트 전용 상태, 화면 조립

### `widgets/`

- 역할: 특정 화면 맥락에서 큰 사용자 경험 단위를 조합하는 레이어
- 대표 예시: 에디터 좌우 패널, 미리보기, 메인 포스터 편집기
- 넣어야 하는 것: 화면 전용 컨텍스트, 조합 컴포넌트, 화면 전용 훅/유틸
- 넣으면 안 되는 것: 범용 primitive, 서버 엔드포인트, 블록 표준 정의

### `components/organisms/`

- 역할: 초대장 블록 단위의 실제 기능 구현
- 대표 예시: `gallery`, `greeting`, `place`, `phone`, `bgm`, `video`
- 넣어야 하는 것: 블록별 컴포넌트, `schema`, `definition`, edit/preview 구현
- 넣으면 안 되는 것: 페이지 진입 책임, 전체 에디터 조립 책임, 범용 공통 레이어 역할

### `components/molecules/`

- 역할: atoms보다 큰 재사용 UI 조합
- 대표 예시: text editor, text field, selector, toast, image editor
- 넣어야 하는 것: 여러 화면/블록에서 재사용 가능한 UI 조합 단위
- 넣으면 안 되는 것: 블록 도메인 규칙, 페이지 흐름, 저장/조회 로직

### `components/atoms/`

- 역할: 가장 작은 UI primitive
- 대표 예시: button, input, image, radio, label
- 넣어야 하는 것: 스타일 가능한 기본 UI 조각
- 넣으면 안 되는 것: 도메인 로직, 블록 상태, 화면 흐름

### `shared/`

- 역할: 공통 타입, 상태, 유틸, 데이터, 정적 리소스를 제공하는 기반 레이어
- 대표 예시: `types`, `store`, `data`, `utils`, `assets`, `hooks`
- 넣어야 하는 것: 여러 레이어에서 재사용되는 타입/유틸/store/registry
- 넣으면 안 되는 것: 특정 화면 전용 조합, 특정 블록의 상세 UI 구현

## 3. 세부 폴더 가이드

### `app/(home)/`

- 홈 화면과 랜딩 흐름을 담당한다.
- 로그인 여부에 따라 홈 UI가 달라지는 진입 지점이다.
- 홈 전용 컴포넌트는 둘 수 있지만, 다른 화면에서도 쓰일 구조는 상위 공통 레이어를 검토한다.

### `app/editor/` 및 `app/editor/[id]/`

- 편집기 진입과 편집 초기화 흐름을 담당한다.
- 에디터 식별자, query param, 초기 데이터 로드의 출발점이 된다.
- 블록 구현 자체는 두지 말고, 조립과 초기화 책임만 둔다.

### `app/guest/[id]/`

- 공개 초대장 렌더링을 담당한다.
- 공개된 Drive JSON을 읽고 검증한 뒤 게스트 화면을 렌더링한다.
- 편집기 전용 로직과 혼합하지 않는다.

### `app/api/auth/`

- 인증 관련 서버 로직을 담당한다.
- OAuth, 세션, 로그인 상태 확인 등 인증 흐름이 여기에 속한다.

### `app/api/drive/`

- 이 프로젝트의 핵심 서버 레이어다.
- 저장, 조회, 수정, 삭제, 배포, 토큰 처리, Drive helper가 여기에 모인다.
- 데이터 저장 구조가 바뀌거나 Drive 연동이 수정되면 이 위치를 우선 본다.

### `widgets/editor/`

- 편집기 화면 전용 조합 레이어다.
- left panel, right panel, preview 같은 편집기 내부 UX 단위를 묶는다.
- 특정 블록 규칙보다 “편집 화면 흐름”에 가깝다.

### `widgets/mainPoster/`

- 메인 포스터 편집기와 캔버스(Fabric) 관련 기능을 담당한다.
- 포스터 편집, 그래픽 제어, rich text, 컨텍스트, Fabric 유틸이 여기에 있다.
- 일반 블록 편집과는 다른 별도 축으로 이해한다.

### `components/organisms/*`

- 블록별 실제 기능 구현 위치다.
- 각 블록은 보통 `definition`, `schema`, 편집 UI, 미리보기 UI를 함께 가진다.
- 블록 하나의 동작이 이상하면 가장 먼저 이 위치를 본다.

### `shared/data/registry/`

- 블록 registry와 schema 조합의 중심이다.
- 어떤 블록이 존재하는지, 어떤 definition과 연결되는지 이해하려면 먼저 본다.

### `shared/store/editorStore/`

- 편집기 전역 상태의 중심이다.
- block, image, UI, drive 관련 slice가 이 구조 아래 모여 있다.
- 편집 상태 흐름을 이해하려면 이 위치를 우선 본다.

### `shared/types/`

- 공통 타입 정의 위치다.
- 블록/에디터 구조를 코드 레벨에서 빠르게 파악할 때 도움이 된다.

### `shared/utils/`

- 여러 레이어에서 재사용되는 범용 유틸 위치다.
- 특정 화면 전용이면 여기보다 원래 맥락 폴더에 두는 것이 더 적절할 수 있다.

### `shared/assets/`

- 아이콘, 이미지 같은 정적 리소스 위치다.
- 기능 로직을 이 위치에 섞지 않는다.

## 4. 작업 유형별 추천 위치

### 새 페이지 추가

- 기본 위치: `app/`
- 페이지 전용 조합이 크면 관련 `widgets/`를 함께 만든다.

### 새 블록 추가

- 기본 위치: `components/organisms/<block-name>/`
- 함께 수정할 가능성이 높은 위치: `shared/data/registry/`, `shared/types/`

### 저장 방식 수정

- 기본 위치: `app/api/drive/`
- 함께 봐야 하는 위치: `shared/store/editorStore/`, `app/editor/[id]/`

### 편집기 패널 UI 수정

- 기본 위치: `widgets/editor/`
- 저수준 입력 UI가 바뀌면 `components/molecules/`, `components/atoms/`도 함께 본다.

### 메인 포스터 캔버스 기능 수정

- 기본 위치: `widgets/mainPoster/`
- 상태/데이터 구조가 연결되면 `shared/store/editorStore/`도 함께 본다.

### 공통 버튼/입력창 수정

- 기본 위치: `components/atoms/` 또는 `components/molecules/`
- 블록 전용 디자인이면 organism 내부에 두는 편이 맞을 수 있다.

## 5. 자주 하는 배치 실수

### `widgets/`를 공용 UI 폴더처럼 쓰는 실수

잘못이다.
`widgets/`는 특정 화면 경험을 조합하는 곳이지, 범용 UI 저장소가 아니다.

### organism 로직을 `app/`에 직접 넣는 실수

잘못이다.
`app/`은 진입과 조립을 담당하고, 블록 기능 구현은 `components/organisms/`가 맡아야 한다.

### 애매하면 전부 `shared/`로 올리는 실수

위험하다.
반복 사용 여부보다 먼저, **정말 맥락 독립적인지**를 확인해야 한다.

### Drive 관련 변경을 클라이언트 코드만 보고 처리하는 실수

잘못이다.
이 프로젝트의 저장 구조 핵심은 `app/api/drive/`에 있다.

### 메인 포스터 기능을 일반 블록처럼 취급하는 실수

주의가 필요하다.
`widgets/mainPoster/`는 별도 축의 편집 경험과 캔버스 로직을 갖고 있어 일반 organism 블록과 동일하게 보면 안 된다.
