# 아키텍처 개요

## 문서 목적

이 문서는 코드 수정 전에 이 프로젝트의 아키텍처를 빠르게 파악하기 위한 참고 문서다.
레포 구조가 일반적인 웹 서비스와 다르게 보이거나, 어떤 레이어가 변경을 소유해야 하는지 판단이 어려울 때 먼저 읽는다.

## 1. 핵심 개념

이 프로젝트는 일반적인 **중앙 백엔드 + 중앙 데이터베이스** 구조의 청첩장 서비스가 아니다.
화면은 Next.js가 제공하지만, 실제 사용자 초대장 데이터는 서비스 운영자의 DB가 아니라 **사용자 개인의 Google Drive**에 저장된다.

이 구조를 이해할 때는 아래 세 가지를 기준으로 본다.

1. **Google Drive가 사실상의 영속 저장소다.**
2. **Next.js의 서버 기능이 백엔드 통합 레이어 역할을 한다.**
3. **편집기는 하나의 거대한 폼이 아니라 블록 기반 편집 시스템이다.**

## 2. 시스템 전체 구조

전체 구조를 크게 나누면 다음과 같다.

- `app/**`: 페이지 진입점과 라우팅, URL 기반 흐름을 담당한다.
- `app/api/**`: 인증, Google Drive 연동, 저장/조회/배포 등 서버 측 처리와 서버 유틸을 담당한다.
- `widgets/**`: 특정 화면 맥락에서 편집 경험을 조합하는 레이어다.
- `components/organisms/**`: 실제 초대장 블록 기능을 구현하는 레이어다.
- `shared/**`: 공통 타입, 레지스트리, 상태, 템플릿, 유틸, 정적 리소스를 제공한다.

공개 게스트 페이지도 내부 DB를 읽는 방식이 아니라, Google Drive에 공개된 JSON을 읽어 렌더링하는 구조다.

## 3. 주요 실행 흐름

### 3.1 홈과 인증 진입 흐름

홈 라우트는 현재 인증 상태를 확인한 뒤 홈 화면을 렌더링한다.
아키텍처 관점에서는 사용자가 초대장 생성/편집 흐름에 진입하는 시작점으로 이해하면 된다.

### 3.2 편집기 진입 및 초기화 흐름

편집기 라우트는 메인 편집 흐름의 진입점이다.
일반적인 흐름은 다음과 같다.

1. `app/editor/**` 아래 라우트가 초대장 식별 정보를 받는다.
2. 페이지 엔트리가 편집기 화면을 조립한다.
3. 클라이언트 훅과 store/context가 편집 상태를 초기화한다.
4. 기존 초대장 데이터가 Drive 관련 API 또는 유틸을 통해 로드된다.
5. widgets와 block 컴포넌트가 현재 초대장 구조를 렌더링한다.

### 3.3 저장 및 수정 흐름

저장은 단순히 에디터 내부 로컬 상태만 다루는 작업이 아니다.
다음과 같이 여러 레이어를 가로지른다.

1. 클라이언트/에디터 상태가 현재 초대장 payload를 구성한다.
2. 클라이언트 코드가 Drive 관련 API 라우트를 호출한다.
3. `app/api/drive/**`가 Google API 연동과 저장 처리를 수행한다.
4. 데이터가 Google Drive 안의 파일과 메타데이터 형태로 저장된다.

### 3.4 공개 초대장 렌더링 흐름

공개 초대장 페이지는 내부 DB를 읽지 않는다.
대신 다음 순서로 동작한다.

1. 게스트 라우트가 공개된 파일 식별자를 받는다.
2. 페이지가 Google Drive 공개 URL에서 JSON을 가져온다.
3. payload를 검증한다.
4. 메인 포스터, 블록 렌더러, BGM 렌더러가 최종 초대장을 구성한다.

## 4. 레이어별 책임

### `app/`

페이지 진입점, 라우팅, URL 기반 흐름, 페이지 수준 조립과 초기화를 담당한다.
재사용 가능한 비즈니스 컴포넌트나 공통 도메인 로직을 두는 곳으로 이해하면 안 된다.

### `app/api/`

Next.js 안에서 백엔드처럼 동작하는 레이어다.
주요 책임은 다음과 같다.

- 인증
- Google Drive 연동
- load/save/update/publish/delete 라우트
- 서버 전용 유틸

저장, 게시, 토큰 갱신, Drive 메타데이터가 관련된 작업이면 이 레이어를 함께 확인한다.

### `widgets/`

특정 화면 맥락에서 여러 요소를 조합하는 레이어다.
에디터 화면처럼 큰 사용자 경험 단위를 만드는 곳으로 이해한다.
여러 하위 컴포넌트와 상태를 사용할 수 있지만, 여전히 특정 화면 흐름에 묶여 있다.

### `components/organisms/`

초대장 블록 단위의 실제 기능 구현 레이어다.
사용자가 보는 초대장 섹션의 동작이 잘못되었다면, 실제 구현은 이 레이어에 있을 가능성이 높다.

### `shared/`

여러 레이어에서 공통으로 쓰는 기반을 제공한다.
예를 들면 다음이 포함된다.

- 공통 타입
- editor store
- registry / schema 데이터
- template 데이터
- 범용 유틸
- 정적 리소스

여기에 코드를 둘 때는 정말로 여러 레이어에서 재사용되는지 먼저 확인한다.
특정 페이지, 특정 widget, 특정 block 맥락에 강하게 묶여 있다면 `shared/`에 두면 안 된다.

## 5. 상태 관리 모델

이 프로젝트를 하나의 전역 store만 있는 구조로 이해하면 안 된다.
상태 소유권은 관심사별로 나뉘어 있다.

핵심 패턴:

- 편집기 전반의 block/drive 관련 상태는 `shared/store/editorStore/**`가 담당한다.
- 메인 포스터/캔버스 관련 상태는 `widgets/mainPoster/**`가 담당한다.
- 특정 기능 전용 상태는 organism 근처에서 따로 관리될 수 있다. 예: BGM store

버그를 추적할 때는 먼저 **어떤 관심사가 상태를 소유하는지**부터 확인하고, 그 다음 업데이트 흐름을 따라간다.
하나의 중앙 store에서 모든 문제가 해결될 것이라고 가정하지 않는다.

## 6. 초대장 데이터 표현 방식

초대장은 하나의 평평한 페이지 객체가 아니라, 여러 **블록(block)** 의 집합으로 모델링된다.
이 블록 기반 구조가 이 프로젝트의 핵심 도메인 모델이다.

도메인 구조를 이해하려면 다음 위치를 우선 본다.

- `shared/data/registry/**`: 블록 registry와 schema 조합 방식
- `shared/types/**`: 공유 타입 정의
- `components/organisms/**`: 블록별 schema, definition, edit UI, preview UI 구현

이 구조를 이해할 때 유용한 관점은 다음과 같다.

- `shared/data/registry/**` = 어떤 블록이 존재하는가, 어떻게 등록되는가
- `components/organisms/**` = 각 블록이 실제로 어떻게 동작하는가
- `shared/store/editorStore/**` = 에디터 상태가 초대장 구조를 어떻게 저장하고 변경하는가

## 7. 처음 읽을 때 추천 순서

프로젝트를 처음 이해할 때는 아래 순서로 읽는 것을 추천한다.

1. `shared/data/registry/` — 블록 모델과 도메인 구조 파악
2. `shared/store/editorStore/` — 편집기 전역 상태와 액션 흐름 파악
3. `app/editor/[id]/` — 편집기 초기화와 편집 진입 흐름 파악
4. `widgets/mainPoster/` — 메인 포스터/캔버스 편집 구조 파악
5. `components/organisms/` — 블록별 실제 구현 확인
6. `app/api/drive/` — Drive 기반 저장/조회/배포 구조 확인
7. `app/guest/[id]/` — 공개 초대장 렌더링 흐름 확인

이 순서를 따르면 페이지 트리만 보고 프로젝트를 단순하게 해석하는 실수를 줄일 수 있다.
먼저 데이터 모델과 상태 구조를 이해한 뒤 화면을 읽는 것이 더 안전하다.

## 8. 자주 생기는 오해

### “DB가 없으니 저장도 없다.”

틀린 해석이다.
저장은 존재하며, 다만 앱 소유 DB가 아니라 Google Drive 기반일 뿐이다.

### “서버가 없으니 전부 클라이언트 로직이다.”

틀린 해석이다.
`app/api/**`와 Next.js의 서버 기능이 백엔드 역할을 수행한다.

### “편집기는 하나의 전역 source of truth만 가진다.”

너무 단순한 해석이다.
상태는 편집기 전역, 포스터 전용, 기능 전용 경계로 나뉘어 있다.

### “`widgets/`는 그냥 재사용 컴포넌트 모음이다.”

틀린 해석이다.
`widgets/`는 특정 화면 맥락을 조합하는 레이어이지, 범용 공통 레이어가 아니다.

### “재사용 가능해 보이면 일단 `shared/`로 보내면 된다.”

위험한 판단이다.
정말로 여러 레이어에서 재사용되고 특정 맥락에 묶여 있지 않을 때만 `shared/`를 고려한다.
