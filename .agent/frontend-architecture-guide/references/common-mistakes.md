## 1. 구조를 잘못 이해하는 실수

### 실수 1. 이 프로젝트를 일반적인 중앙 DB 기반 서비스처럼 해석한다

잘못이다.
이 프로젝트는 사용자 데이터를 서비스 운영자 DB가 아니라 사용자 개인 Google Drive에 저장하는 구조다.
따라서 저장/조회/배포 문제는 일반적인 CRUD API처럼만 보면 안 된다.

### 실수 2. “서버가 없다”고 생각하고 전부 클라이언트 코드만 본다

잘못이다.
Next.js의 `app/api/**`가 사실상 서버 통합 레이어 역할을 한다.
인증, 저장, 조회, 배포, 토큰 갱신 같은 핵심 로직은 이 레이어를 같이 봐야 한다.

### 실수 3. 공개 게스트 페이지와 편집기 페이지를 같은 흐름으로 본다

잘못이다.
편집기는 편집 상태와 저장 흐름을 다루고, 공개 게스트 페이지는 공개된 Drive JSON을 읽어 렌더링하는 별도 흐름이다.
두 흐름은 목적과 책임이 다르다.

## 2. 파일 위치를 잘못 고르는 실수

### 실수 4. `widgets/`를 범용 공용 컴포넌트 폴더처럼 사용한다

잘못이다.
`widgets/`는 특정 화면 경험을 조합하는 레이어다.
에디터 좌우 패널, 미리보기, 메인 포스터 편집기처럼 화면 맥락이 강한 구조만 둔다.

### 실수 5. `app/`에 블록 기능 구현을 넣는다

잘못이다.
`app/`은 페이지 진입과 조립을 담당한다.
블록의 실제 기능 구현은 `components/organisms/`에 두어야 한다.

### 실수 6. 애매하면 전부 `shared/`에 넣는다

위험하다.
`shared/`는 공통 기반 레이어이지 “어디 둘지 모르겠는 코드 모음”이 아니다.
특정 페이지, 특정 widget, 특정 block에 강하게 묶여 있다면 원래 맥락 레이어에 남겨야 한다.

### 실수 7. 저수준 UI와 도메인 로직을 한 파일에 섞는다

잘못이다.
`components/atoms/`, `components/molecules/`는 재사용 UI 조각 중심으로 유지하고, 블록 도메인 규칙은 organism이나 registry 쪽에서 관리해야 한다.

## 3. 상태를 잘못 다루는 실수

### 실수 8. 편집기 전체 상태가 하나의 전역 source of truth라고 가정한다

너무 단순한 해석이다.
편집기 전역 상태는 `shared/store/editorStore/**`에 있지만, 메인 포스터는 `widgets/mainPoster/**`, BGM은 organism 근처 store처럼 관심사별 상태가 분리되어 있다.

### 실수 9. 상태 문제를 볼 때 UI만 수정한다

위험하다.
UI 버그처럼 보여도 실제 원인은 store slice, 초기화 훅, 데이터 구조, 저장 결과일 수 있다.
문제가 화면에 보인다고 해서 원인이 화면 레이어에만 있다고 가정하면 안 된다.

### 실수 10. 메인 포스터 상태를 일반 블록과 동일하게 다룬다

주의가 필요하다.
`widgets/mainPoster/**`는 Fabric 기반 캔버스 편집이라는 별도 축을 갖고 있어서 일반 organism 블록과 같은 방식으로만 보면 안 된다.

## 4. Drive 연동을 잘못 이해하는 실수

### 실수 11. 저장 문제를 클라이언트 코드에서만 찾는다

잘못이다.
이 프로젝트의 저장 구조 핵심은 `app/api/drive/**`에 있다.
클라이언트는 저장 요청을 보내더라도, 실제 Drive 처리와 저장 규칙은 서버 레이어에서 결정된다.

### 실수 12. “DB가 없으니 persistence도 없다”고 생각한다

잘못이다.
저장은 존재한다.
다만 중앙 DB가 아니라 Drive 기반 파일/메타데이터 저장 구조일 뿐이다.

### 실수 13. 공개 초대장도 내부 API를 통해서만 렌더링된다고 가정한다

잘못이다.
공개 게스트 페이지는 공개된 Drive JSON을 직접 fetch하는 흐름을 가진다.
따라서 공개 렌더링 문제는 편집기 저장 문제와 구분해서 봐야 한다.

## 5. 블록 구조를 잘못 이해하는 실수

### 실수 14. 초대장을 하나의 거대한 폼 객체로 생각한다

잘못이다.
이 프로젝트의 초대장은 block 기반 구조다.
블록 단위의 schema, definition, registry, preview/edit 구현을 함께 이해해야 한다.

### 실수 15. 블록 정의와 블록 구현을 같은 레이어에만 있다고 생각한다

잘못이다.
블록 registry와 schema 조합은 `shared/data/registry/**` 쪽에서 읽어야 하고, 실제 UI와 동작은 `components/organisms/**`에서 읽어야 한다.
둘 중 하나만 보면 구조를 절반만 이해하게 된다.

### 실수 16. 새 블록을 추가하면서 registry를 수정하지 않는다

잘못이다.
새 block 기능은 organism 구현만으로 끝나지 않는다.
보통 registry, 타입, 편집기 상태 흐름까지 함께 확인해야 한다.

## 6. 작업 전에 확인할 체크리스트

### 새 기능 추가 전

- 이 기능이 페이지 책임인지, widget 책임인지, organism 책임인지 먼저 판단했는가?
- 저장/조회가 관련되면 `app/api/drive/**`까지 같이 볼 계획인가?
- 기존에 유사한 구현이 이미 있는지 먼저 찾았는가?

### 버그 수정 전

- 문제가 시작되는 진입 페이지를 확인했는가?
- 상태 소유 위치가 어디인지 먼저 확인했는가?
- 화면에 보이는 문제와 실제 원인이 다른 레이어일 수 있음을 고려했는가?

### 리팩터링 전

- 이 코드를 정말 `shared/`로 올려도 되는지 판단했는가?
- 페이지 조립 책임과 블록 구현 책임이 섞이지 않게 유지하고 있는가?
- 메인 포스터, 일반 block, Drive 연동을 같은 종류의 코드처럼 단순화하지 않았는가?
